# 기술 선택 기록: 왜 Tauri + Rust 인가

Git GUI 를 만들기 전에 어떤 방식·언어로 만들지 여러 후보를 비교했다. 이 문서는 그 비교와 결정 이유를 남긴다.
나중에 상황이 바뀌어 다시 판단해야 할 때 "왜 이렇게 했는지"를 확인하는 용도다.

- 작성: 2026-10-07
- 결정: **데스크톱 앱 = Tauri 2 (Rust) + React/TypeScript 화면**, **AI 서버 = NestJS (TypeScript)**

---

## 1. 무엇을 만드는가 (판단 기준)

비개발자(특히 AI 코딩 도구로 프로그램을 만드는 사람)가 Git 을 몰라도 저장·올리기·되돌리기·협업을 할 수 있게 돕는 **데스크톱 Git 클라이언트**.

이 제품의 성격에서 나온 판단 기준:

| 기준 | 왜 중요한가 |
|---|---|
| **내 컴퓨터의 폴더와 git 을 다룰 수 있어야 함** | Git 클라이언트의 본질. 브라우저만으로는 불가능 |
| **설치 파일이 작고 가벼워야 함** | 비개발자는 큰 다운로드·무거운 앱에서 쉽게 이탈. AI 코딩 도구(Cursor 등)와 함께 켜 두는 앱이라 메모리도 중요 |
| **안전해야 함** | 사용자 코드, API 키, GitHub 로그인 정보를 다룬다. 실수로 코드를 날리면 안 됨 |
| **화면 표현력** | Git 그래프, 터미널 블록, 충돌 비교, 드래그로 크기 조절 등 화면이 복잡함 |
| **이미 만든 프로토타입 재사용** | React + TypeScript 로 만든 클릭형 프로토타입이 있었음 |
| **혼자 개발 가능** | 개발자는 1명. Python·TypeScript·NestJS 에 익숙하고 Rust·Go 는 처음 |

## 2. 첫 번째 질문: 웹이냐, 데스크톱(.exe)이냐

| | 웹 앱 | 데스크톱 앱 (.exe) |
|---|---|---|
| 설치 | 없음 (링크만) | 설치 필요 |
| 내 컴퓨터 폴더 읽기/쓰기 | ❌ 거의 불가 (일부 브라우저만, 매번 권한 요청) | ✅ |
| git 실행 | ❌ 불가 | ✅ |
| GitHub 로그인 정보 보관 | ❌ 어려움 | ✅ (OS 보안 저장소 / Git Credential Manager) |

**결론: 제품은 데스크톱 앱.** 웹은 Git 을 다룰 수 없다.
대신 웹은 **데모·사용자 테스트·소개용**으로 같이 쓴다 → 지금 GitHub Pages 에 올려 둔 웹 데모가 그 역할.

## 3. 데스크톱 앱을 만드는 방법 비교

".exe 니까 C++ 이나 Go" 라고 생각하기 쉽지만, .exe 는 결과물 형식일 뿐 어떤 언어로든 만들 수 있다.
진짜 차이는 **화면을 무엇으로 그리느냐**와 **내부 로직을 어떤 언어로 짜느냐**에서 난다.

### 3.1 후보 한눈에 보기

| 방식 | 화면 | 내부 로직 | 설치 크기 | 메모리 | 화면 표현력 | 배우기 | 판단 |
|---|---|---|---|---|---|---|---|
| **Tauri 2** | 웹 기술(React) | **Rust** | 매우 작음 | 작음 | 높음 | Rust 가 어려움 | ✅ **선택** |
| Wails | 웹 기술(React) | Go | 작음 | 작음 | 높음 | Go 는 쉬움 | 차선 |
| Electron | 웹 기술(React) | TypeScript(Node) | 큼 (80~150MB) | 큼 (수백 MB) | 높음 | 지금 바로 가능 | 무거움 |
| C++ + Qt | Qt 위젯 | C++ | 작음 | 작음 | 보통 (만들기 느림) | 어려움 | 비용이 큼 |
| 완전 네이티브 | WinUI / SwiftUI | C# / Swift | 작음 | 작음 | 높음 | OS 마다 따로 | 1인 개발에 비효율 |
| Python (PySide 등) | Qt 위젯 | Python | 큼 (런타임 포함) | 보통 | 낮음~보통 | 이미 익숙 | 화면 품질 한계 |
| Go 순수 GUI (Fyne) | 자체 위젯 | Go | 작음 | 작음 | 낮음 | 쉬움 | 표현력 부족 |
| Rust 네이티브 UI (egui, iced) | 자체 위젯 | Rust | 작음 | 매우 작음 | 낮음~보통 | 어려움 | 생태계 미성숙 |

### 3.2 후보별 판단

**Electron** — 가장 무난하고 자료가 많다(GitHub Desktop, GitKraken, VS Code 가 이 방식). 지금 실력으로 바로 만들 수 있다.
하지만 Chromium 을 통째로 넣어서 설치 파일이 80~150MB, 메모리도 수백 MB. Cursor 같은 무거운 AI 도구와 함께 켜 둘 비개발자용 앱에는 부담이 크다.

**C++ + Qt** — 성능과 안정성은 검증됨(Sublime Merge 는 자체 C++ UI). 하지만 그래프·충돌 비교 같은 화면을 만드는 속도가 웹보다 몇 배 느리고, 메모리 관련 버그를 직접 관리해야 한다. 혼자 만드는 제품에는 비용이 너무 크다.

**Python (PySide 등)** — 가장 익숙한 언어지만 지금 같은 화면(GitKraken 스타일 그래프, Warp 스타일 터미널)을 만들기 어렵고 결과물이 투박해지기 쉽다. 프로토타입을 다시 만들어야 한다.

**Go 순수 GUI / Rust 네이티브 UI** — 빠르고 가볍지만 위젯 생태계가 약해서 커스텀 그래프나 터미널 블록 같은 화면을 만들기 어렵다.

**완전 네이티브(C#/WinUI, Swift)** — 체감 품질은 최고지만 Windows 와 Mac 을 따로 만들어야 한다. 1인 개발에 비효율.

→ **"화면은 웹 기술(React), 내부 로직만 다른 언어"** 인 방식(Tauri, Wails, Electron)이 이 제품에 맞다.
프로토타입을 그대로 쓸 수 있고, 화면 표현력이 높고, Windows/Mac 을 함께 지원한다. 남은 비교는 이 셋이다.

## 4. 최종 비교: Tauri(Rust) vs Wails(Go) vs Electron(TS)

| 항목 | Tauri 2 (Rust) | Wails (Go) | Electron (TS) |
|---|---|---|---|
| 프레임워크 상태 (2026-10 기준) | **v2 안정판이 최신** (2024-10 정식) | v2 안정판은 기능이 오래됨, **v3 는 아직 베타** (2026-08 beta.12) | 안정, 성숙 |
| 설치 파일 | 수 MB | 10MB대 | 80~150MB |
| 메모리 | 수십 MB | 수십 MB | 수백 MB |
| 웹뷰 | OS 내장 (Windows: WebView2) | OS 내장 (WebView2) | Chromium 포함 |
| 자동 업데이트 | 공식 플러그인 | v2 는 직접 구현 | 성숙 (electron-updater) |
| 권한 관리 | **화면이 쓸 수 있는 기능을 하나씩 허용하는 권한 시스템** | 등록한 Go 함수는 화면에서 다 호출 가능 | Node 권한이 넓어 설정 실수 시 위험 |
| 메모리 안전성 | **Rust 컴파일러가 보장** | GC 언어라 안전 | 안전 |
| 내부 언어 난이도 | **어려움** (소유권·빌림 개념) | 쉬움 | 지금 바로 가능 |
| 컴파일 속도 | 느림 (첫 빌드 수 분) | 매우 빠름 | 빌드 불필요 |
| 커뮤니티·자료 | 큼 | 작음 | 가장 큼 |
| 모바일 | 지원 (이 제품엔 불필요) | 미지원 | 미지원 |

### 4.1 왜 Electron 이 아닌가
설치 크기와 메모리. 비개발자용 앱에서 "가볍다"는 것 자체가 기능이다. 화면은 똑같이 React 라 Electron 의 장점(같은 화면 재사용)은 Tauri 도 갖고 있다.

### 4.2 왜 Wails(Go)가 아닌가
Go 는 Rust 보다 훨씬 배우기 쉽고(기초 1~2주 vs 1~3개월), Wails 는 화면에서 부를 함수의 TypeScript 타입을 자동 생성해 주는 등 편한 점이 많다. 하지만:
- **지금 시작하면 v2(안정판, 기능 오래됨)와 v3(베타) 중 골라야 한다.** 여러 창 지원 등 필요한 기능은 v3 에 있다.
- **자동 업데이트·세밀한 권한 관리**를 직접 만들어야 한다. 비개발자용 .exe 제품에서는 둘 다 필수다.
- 자료와 플러그인이 Tauri 보다 적어서, 혼자 배우며 만들다 막혔을 때 불리하다.

### 4.3 왜 Tauri(Rust)인가
- **제품 기반으로 가장 안전하다** — 안정판이 최신, 자동 업데이트·권한 시스템이 공식 제공.
- **가장 가볍다** — 실제로 만들어 보니 실행 파일 약 9MB, 설치 파일 약 2MB.
- **Rust 의 어려운 부분을 상당히 피할 수 있다** — 이 앱에서 Rust 가 하는 일은 "git 실행 + 결과 해석 + 파일 읽기"가 대부분이다. 화면과 상태 관리는 TypeScript 에 두고 Rust 는 얇게 시작했다. 라이프타임·unsafe 같은 어려운 개념은 거의 쓰지 않는다.
- **Rust 를 배울 의향이 있었다** — "배우기 어렵다"가 Tauri 의 가장 큰 단점이었는데, 배울 의향이 있으면 그 단점이 줄어든다.

## 5. "AI 서버까지 Go 로 통일하면?" 에 대한 판단

Go 로 앱(Wails)과 서버를 모두 짜면 언어가 하나로 통일된다는 장점이 있어 보였다. 하지만:

| 조합 | 쓰는 언어 | 새로 배울 언어 |
|---|---|---|
| Wails + Go 서버 | TS(화면) + Go | Go |
| **Tauri + NestJS 서버** | TS(화면·서버) + Rust | **Rust 하나** |
| Tauri + Go 서버 | TS + Rust + Go | Rust, Go (오히려 늘어남) |

- 화면이 어차피 TypeScript 라서 **"언어 하나로 통일"은 애초에 불가능** — 어느 쪽이든 두 언어.
- 앱과 서버는 HTTP 로 JSON 만 주고받아 공유할 코드가 거의 없다.
- AI 서버는 얇다(Claude 호출, 사용량 관리, 나중에 결제). 이미 잘하는 NestJS 로 가장 빨리 만들 수 있다.

→ 통일의 이득은 작고, Tauri + NestJS 가 새로 배울 언어를 Rust 하나로 줄인다.

## 6. AI 서버: 왜 NestJS 인가

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **NestJS** | 화면(React)과 같은 TypeScript → 요청/응답 타입 공유 쉬움. 스트리밍 쉬움. **이미 잘함** | 작은 서버에는 구조가 다소 무거움 | ✅ **선택** |
| FastAPI | 코드가 짧고 빠르게 만듦. 나중에 Python AI 도구(코드 분석 등) 쓰기 좋음. 이미 잘함 | 화면과 타입 공유에 한 단계(OpenAPI 생성) 더 필요 | 동급 대안 |
| Django | 관리자 화면·로그인·DB 기본 제공 | AI 스트리밍 같은 비동기는 덜 자연스러움 | 관리자 화면이 급하면 고려 |
| Flask | 가장 가벼움 | 부품을 직접 조립. 새로 시작하면 FastAPI 가 거의 모든 면에서 나음 | 제외 |
| Spring Boot | 국내 채용 시장에서 가치가 큼, 대규모에 강함 | 이 규모엔 무겁고, 아직 도움이 필요한 스택이라 개발이 가장 느림 | 포트폴리오 목적이면 재고 |

NestJS 와 FastAPI 의 차이는 크지 않았다. **화면과 같은 언어(TypeScript)** 라는 점에서 NestJS 를 골랐다.

## 7. 지금 구성

```
┌──────────── 데스크톱 앱 (Tauri 2, .exe 약 9MB) ───────────┐
│ 화면: React + TypeScript + Tailwind  (프로토타입 그대로)   │
│        ↕ invoke (화면 ↔ Rust 명령, 별도 스레드에서 실행)    │
│ 내부: Rust — git CLI 실행, 결과 해석, 백업·되돌리기 등      │
└──────────────────────┬─────────────────────────────────────┘
                       │ HTTP (변경 내용 요약만, 비밀 파일 제외)
┌──────────────────────▼─────────────────┐
│ AI 서버: NestJS + Anthropic SDK (Claude)│  API 키는 여기에만
└─────────────────────────────────────────┘

웹 데모 (GitHub Pages): 같은 React 화면을 데모 모드로만 배포
```

## 8. 이 선택의 약점과 대응

| 약점 | 영향 | 대응 |
|---|---|---|
| Rust 학습 곡선 | 초반 개발 속도 저하 | Rust 는 git 실행·해석 위주로 얇게 유지. 코드마다 한국어 설명 주석, 단위 테스트로 동작 고정 |
| OS 마다 웹뷰가 다름 (Windows WebView2 / Mac WebKit) | 같은 화면이 미세하게 다르게 보일 수 있음 | 지금은 Windows 우선. Mac 지원 시 별도 테스트 |
| PC 에 설치된 git 에 의존 | git 이 없는 PC 에서는 실제 저장소 기능 불가 | 다음 단계에서 git 을 앱에 내장 (Windows 용 MinGit) |
| 코드 서명 없음 | 실행 시 "Windows 의 PC 보호" 경고 | 정식 배포 전 서명 인증서 도입 |
| 첫 Rust 빌드가 느림 | 개발 중 대기 시간 | 이후 빌드는 증분이라 수십 초 |

## 9. 다시 판단해야 하는 경우

- **Rust 때문에 개발이 계속 막힐 때** → Wails v3 가 안정판이 되었다면 Go 로 옮기는 것을 재검토 (화면 코드는 그대로 재사용 가능)
- **Mac 사용자가 많아져 웹뷰 차이 문제가 커질 때** → Electron 재검토
- **AI 서버에서 무거운 코드 분석이 필요해질 때** → 그 부분만 Python(FastAPI) 서비스로 분리
- **취업 포트폴리오 목적이 커질 때** → 서버를 Spring Boot 로 다시 만드는 것을 고려
